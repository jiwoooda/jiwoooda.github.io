OVERVIEW

쇼핑 Agent는 대화를 잘하는 것만으로
충분하지 않았습니다

사용자는 상품 탐색, 비교, 수정, 질문, 장바구니 조작, 결제를 하나의 대화 안에서 반복합니다.

“응, 그걸로 해”“아까 거 말고 싼 걸로”“잠깐, 배송지는 어디야?”

같은 발화도 현재 진행 중인 상태에 따라 서로 다른 행동을 의미합니다. 그래서 딸랑구는 단순 챗봇이 아니라, 대화 맥락과 transaction state를 지속적으로 관리하는 Agent로 설계했습니다.

LLM은 의미를 이해하고, 코드는 행동을 통제합니다.
온보딩·스몰토크 → 추천·장바구니 → 배송지 확인 → 결제로 이어지는 음성 중심 쇼핑 흐름

CASE 01

Stateful Agent Architecture

RESULT
19개 노드LangGraph 기반 멀티에이전트 워크플로우
PROBLEM

멀티턴 쇼핑에서는 같은 발화도 현재 상품, 장바구니, 결제 상태에 따라 다른 행동을 의미했습니다.

대화 기록만으로 상태를 추론하면 잘못된 단계 이동이나 이전 행동의 재실행이 발생할 수 있었습니다.

ACTION

LangGraph workflow를 구성하고 ShoppingState에 stage · pending_action · selected_product · cart · payment를 명시적으로 관리했습니다.

Intent / Context / Product / Response / Payment / Recovery 역할을 분리하고, 각 노드가 필요한 상태만 읽고 갱신하도록 구성했습니다.

WHY
Agent를 단순한 prompt chain이 아니라 명시적인 state machine으로 설계해야 멀티턴 거래 흐름을 예측 가능하게 통제할 수 있다고 판단했습니다.
Flexible reasoning, deterministic action.
선호 수집·응답 생성은 Agent가 유연하게, 추천·재주문·결제는 예측 가능한 워크플로우로 분리
CASE 02

노드별 모델 선택 및 Local LLM 실험

RESULT
4개 노드 평가2개 노드에 Qwen3 Local 채택
PROBLEM

모든 노드에 같은 모델을 쓰면 작업별로 다른 정확도·지연시간·비용 요구를 반영하기 어려웠습니다.

Intent 분류와 응답 생성은 필요한 능력도, 평가 기준도 달랐습니다.

ACTION
Intent 분류 · 상품 추천·정렬 · 구매 맥락 구성 · 응답 생성 4개 노드를 분리해, API 모델과 Qwen3 Local을 동일 평가셋·동일 조건에서 비교했습니다.
WHY
Agent 성능은 “가장 좋은 모델 하나”를 고르는 문제가 아니라, 각 노드의 역할에 맞게 품질·지연·비용을 최적화하는 시스템 설계 문제라고 판단했습니다.
노드평가 기준근거최종 선택

CASE 03
COMPONENT EVALUATION

Intent & Slot Routing 개선

RESULT
83.3% → 100%LangSmith Component Regression동일 회귀 평가셋 기준, prompt refinement 이후
PROBLEM

구매·수정 의도를 혼동하거나, 상품 규격 숫자를 실제 구매 수량으로 잘못 해석하는 intent / slot routing 오류가 반복되었습니다.

  • 풀무원 말고 CJ 두부 최저가로 찾아줘refine인데 buy로 분류
  • 계란 10구짜리 두 판 사줘quantity=2가 아니라 20으로 해석
  • 다섯 개로 바꿔줘quantity_change가 아니라 confirm으로 분류
ACTION

실패 케이스를 LangSmith evaluation set으로 구성하고, intent classification과 slot extraction prompt를 개선했습니다.

  • 상품 규격 숫자와 실제 구매 수량 분리
  • buy / refine 경계 명확화
  • confirm / quantity_change 경계 명확화
  • 한국어 수량 표현 처리
WHY

멀티에이전트 시스템에서는 초기 routing 오류가 Product · Cart · Payment 등 downstream 노드 전체로 전파됩니다.

그래서 downstream 예외를 하나씩 추가하기보다, 상위 intent / slot routing 단계의 정확도를 먼저 안정화했습니다.

CASE 04

상품 선택·결제의 결정론적 통제

RESULT
추천과 구매 결정 분리
2단계 Product ValidationHITL Confirmation Gate
PROBLEM

LLM이 추천과 실제 구매 결정을 함께 맡으면, 요청한 상품이 없을 때 비슷한 상품을 임의로 골라버릴 수 있었습니다.

결제 단계의 잘못된 state transition은 실제 거래 오류로 이어질 수 있었습니다.

ACTION

ProductRequest에 match_mode와 allow_substitution을 명시하고, 추천 이후 product identity를 다시 확인하는 2단계 validation을 추가했습니다.

결제는 HITL confirmation gate · pending_action · idempotency guard로 분리해 통제했습니다.

WHY

“추천할 만한 상품”과 “실제로 구매해도 되는 상품”은 다른 문제이기 때문입니다.

중요한 행동은 LLM의 확률적 판단이 아니라 코드로 검증 가능해야 한다고 판단했습니다.

AI 판단(무엇이 중요한가)과 코드 계산(점수·필터)을 분리한 추천 파이프라인 — 안전·명시 조건 필터링 후 최종 후보 선정
CASE 05
RELIABILITY / RECOVERY

Recovery / Fallback Architecture

RESULT
복구 가능한 실패와
안전 종료 경로를 분리
Failure DetectionRecoveryClarificationSafe Stop
PROBLEM

초기에는 재시도, clarification, 반복 실패, 최종 종료가 하나의 fallback 흐름에 섞여 있어, 복구 가능한 오류와 더 이상 자동 복구하면 안 되는 상황을 구분하기 어려웠습니다.

그래서 같은 실패가 반복되거나, 복구 이후 다시 Recovery로 진입하는 문제가 생겼습니다.

ACTION

실패를 FailureEvent로 구조화하고 역할을 분리했습니다.

  • Recovery — 자동 복구 또는 사용자 clarification
  • Fallback — 복구 불가 시 검증된 상태를 유지한 채 safe stop
  • Terminal boundary — fallback 이후 같은 턴에서 재진입 차단

또한 일반 대화는 Recovery 흐름과 분리했습니다.

WHY

문장별 예외 처리를 추가하는 대신, “어느 단계에서 어떤 실패가 발생했는가”를 기준으로 복구해야 새로운 입력에도 확장 가능한 구조를 만들 수 있다고 판단했습니다.

Recovery는 정상 workflow 복귀, Fallback은 더 이상 자동 행동하지 않는 안전 종료로 역할을 나눴습니다.

Recovery는 복구를 담당하고, Fallback은 안전한 종료를 담당합니다.
Failure Detection → FailureEvent → Recovery Orchestrator(Recover · Clarify · fallback_required) → Fallback Handler → Safe Stop → Turn 종료

PROBLEM
Unit test와 component regression은 기능 단위 오류는 찾았지만, 여러 turn을 거치며 생기는 상태 붕괴와 사용자 이탈은 충분히 보여주지 못했습니다.
ACTION

고령 사용자의 말투·디지털 숙련도·행동 특성을 반영한 4 Persona × 4 Scenario E2E simulation을 수행했습니다.

각 transcript에서 Trust · Frustration · Ease뿐 아니라 실제 system failure와 root cause를 추출하고, 이를 코드 수정 → regression test로 다시 반영했습니다.

WHY
Agent의 품질은 한 번의 응답 정확도보다, 사용자가 여러 turn 동안 목표를 끝까지 달성할 수 있는지로 평가해야 한다고 판단했습니다.
COMPONENT

CASE 03의 83.3% → 100%는 Intent·Slot Routing 단일 단계의 회귀 평가 결과입니다.

E2E SYSTEM

이 CASE의 3/16 → 7/16, 7/16 → 1/16은 persona 기반 multi-turn 시스템 전체 평가 결과입니다.

두 수치는 서로 다른 범위를 측정하며, 직접 비교할 수 있는 동일 지표가 아닙니다.
Evaluation→Failure→Root Cause→Fix→Regression
1차 평가 진단 리포트 — 직접·모호·주제 이탈 시나리오에서 반복적으로 붕괴
장바구니 수정 중 배송지·결제 질문 → 거래 맥락 상실, 신뢰 하락·좌절 상승
전체 성공률뿐 아니라 failure 유형별 발생 빈도를 비교해, 개선된 문제와 새롭게 드러난 문제를 다음 iteration의 우선순위로 반영했습니다.
추가 자료 — 장바구니 삭제 실패 사례
여러 세션에서 삭제 요청이 추가로 해석됨 — 문장 문제가 아니라 기능(capability) 누락이었음

LEARNINGS

배운 것

01

Agent의 실패는 모델의 실패와 같지 않다

State, Routing, Tool, Capability 문제를 분리해서 봐야 했습니다.

02

LLM은 모든 곳에 사용할 필요가 없다

의미 해석에는 유연함이 필요하지만, 거래 행동은 결정론적으로 통제하는 것이 더 안정적이었습니다.

03

평가는 점수를 만드는 작업이 아니라 시스템을 바꾸는 작업이다

발견한 failure가 코드 수정과 regression test로 이어질 때, 평가가 실제 시스템 개선으로 연결됐습니다.
